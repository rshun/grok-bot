# 进度消息、表情回应、发送文件、接收图片：设计说明

日期：2026-10-27
分支：`dev-chat-actions`（基于 `origin/master` 1dc5880，已包含 bubblewrap 回退）
参照：Claude Code 官方 Telegram / Discord channel 插件（`anthropics/claude-plugins-official` 的 `external_plugins/telegram`、`external_plugins/discord`）

## 1. 背景和目的

用户对比了 Claude Code 官方的 Telegram / Discord 插件，希望 grok-bot 也能做到其中四件事：

1. **修改已发的消息**：处理过程中显示进度，做完后把进度消息改成最终回答。
2. **加表情回应**：Grok 可以给用户的消息加表情，简单的确认不必再写一段话。
3. **发送文件**：Grok 可以把服务器上的文件直接发到聊天里。
4. **接收图片**：用户发图片，Grok 能看到图片内容。

Claude Code 插件的做法是把消息送进一个一直在运行的会话，由 Claude 调用 `reply`、`react`、`edit_message` 等工具。grok-bot 是每条消息跑一次 `grok -p`，回答由 bot 发出。所以本设计保留 bot 发送回答的方式，只把"加表情""发文件"做成 Grok 可以调用的工具，进度和图片由 bot 自己处理。

## 2. 目标、非目标、反目标

**目标**

- 普通聊天消息处理期间有一条会更新的进度消息，最后变成回答本身。
- Grok 能给触发本轮的那条用户消息加表情。
- Grok 能把服务器上的文件发到当前聊天，规则与沙箱读取规则一致。
- 用户发来的图片（含说明文字）能交给 Grok。

**非目标**

- 群组、Discord 服务器频道。用户明确不要。
- 读取历史消息（Discord `fetch_messages`、Telegram 自建消息记录）。用户明确不要。
- 接收语音、视频、贴纸和非图片文件。仍回复"暂不支持"，文案可调整。
- 远程审批工具调用（Claude Code 的 permission relay）。grok-bot 没有需要审批的动作。
- 开放 `image_gen` 等生成类工具。
- 给其他消息加表情、往其他聊天发东西。
- 修改数据库结构。

**反目标（即使功能能用，出现以下情况也算失败）**

- 借"发送文件"拿到沙箱禁止读取的文件：grok 登录凭证、`~/.ssh`、`BOT_ENV_FILE`、`bot.db*`、任何 `.env`、任何 `.pem`，包括经软链接绕过。
- 一个聊天的 Grok 能对另一个聊天加表情或发文件。
- 本机其他进程、网页内容或文件内容能冒充某一轮调用 bot 的工具。
- 进度更新触发平台限流，导致最终回答发不出去。
- 现有行为退化：引用原消息、长回复分段、排队提示、命令回复、Discord 斜杠命令、定时任务结果、写入授权确认、`/reset` 提醒。

## 3. 用户已经决定的

| 事项 | 决定 |
|---|---|
| 要做的功能 | 修改已发消息（进度）、加表情回应、发送文件、接收图片 |
| 不做的功能 | 群组 / 服务器频道、读取历史消息 |
| 发送文件的范围 | 和 Claude Code 一致：Grok 能读的都能发；沙箱禁止读取的一律不能发，软链接按真实路径检查 |
| 文件功能关闭时 | 发送文件一起关闭 |
| 进度消息 | 先发"处理中…"，过程中更新，做完改成回答；长回答第一段沿用该消息，其余新发；出错改成错误提示 |
| 表情 | 只能加在当前这条用户消息上；只加表情、不写文字也可以，此时删掉进度消息 |
| 图片 | 支持照片和以文件形式发来的图片，说明文字一起交给 Grok |
| 定时任务 | 可以发文件，不能加表情 |
| 图片传递方式不可行时 | 回来和用户重新商量，不自行换方案 |

## 4. 设计

### 4.1 Grok 调用 bot 的通道：本地 MCP 服务 *（我定的）*

bot 进程内启动一个 MCP 服务（Streamable HTTP），只监听 `127.0.0.1` 的随机端口，提供两个工具：`react` 和 `send_file`（4.3、4.4）。Grok 现在就能通过 `search_tool` / `use_tool` 调用 MCP，不需要开放新的内置工具。

**接入 grok**：bot 启动时写入 `DATA_DIR/workspace/.grok/config.toml`（grok 的 `--cwd` 就是这个目录，属于项目级 MCP 配置），内容大致为：

```toml
# managed by grok-bot; do not edit
[mcp_servers.grokbot]
url = "http://127.0.0.1:<端口>/mcp"
headers = { Authorization = "Bearer ${GROKBOT_TURN_TOKEN}" }
```

- 与 `sandbox.toml` 一样：第一行是标记，文件存在但不是 bot 生成的就不覆盖，此时两个工具不可用，聊天照常。
- 不修改用户级 `~/.grok/config.toml`。
- 文件里没有秘密。令牌只通过环境变量传给每一次 grok 进程。

**每一轮的身份**：每次调用 grok 前，bot 生成一个随机令牌（不少于 128 位），登记"令牌 → 本轮上下文"，并设置环境变量 `GROKBOT_TURN_TOKEN`。上下文包括平台、聊天 ID、触发消息 ID（定时任务为空）、本轮是否允许发文件、本轮待发文件列表。grok 进程结束后注销令牌。没有令牌、令牌不对或已注销的请求一律拒绝。工具参数里**没有**聊天 ID 和消息 ID，目标完全由令牌决定，满足"不能碰其他聊天"。

**信任边界** *（我定的）*：令牌放在环境变量里，同一系统用户的进程能读到（`/proc/<pid>/environ`），grok 以 stdio 方式拉起的其他 MCP（如 Theseus-mcp）也可能继承这个变量。这些进程本来就能直接读到 `BOT_ENV_FILE` 和 `bot.db`，所以同一系统用户及 grok 的子进程都视为可信，不额外防护。反目标里的"本机其他进程"指其他系统用户的进程。即便令牌被这些进程拿到，也只能在本轮结束前，对本轮这个聊天加表情或发文件，而且仍要经过 4.4 的检查。

**实现**：只用标准库实现 MCP 所需的最小 JSON-RPC 子集（`initialize`、`tools/list`、`tools/call`、通知），不新增依赖。如果实现时发现必须引入 MCP SDK，先停下来征求用户同意（全局规范禁止擅自新增依赖）。

**系统提示词**：在 `promptBase` 后追加一句，告诉 Grok 有 `grokbot` 的 `react` 和 `send_file` 两个工具及各自用途；`send_file` 只在本轮允许时提及。JSON-schema 调用（定时任务解析）不变，仍关闭所有 MCP。

### 4.2 进度消息

**范围**：只用于普通聊天消息（包括图片消息）。命令、Discord 斜杠命令、排队提示、权限提示不变。定时任务不发进度消息，结果仍在结束时一次发出。

**流程**：

1. 👀 / 输入状态仍在**入队时**加，与现在一样，排队中的消息也能立即看到回执。消息**轮到处理时**，再发一条引用原消息的"处理中…"。Discord 的输入状态只持续几秒，处理开始时可以再触发一次。
2. grok 改用流式输出（4.2.1），bot 读到工具调用事件时更新这条消息，例如"正在搜索：xxx"、"正在打开网页"、"正在读取 /srv/a.log"、"正在调用工具：yyy"。内容截断到一行。
3. 两次更新之间至少间隔 3 秒；内容没变就不更新。Telegram 对相同内容的编辑会报错，必须避免。
4. 结束后：
   - 有回答：把进度消息改成回答的第一段；其余段落照现在的方式新发，并引用原消息。写入授权确认行和 `/reset` 提醒仍按现在的位置拼进回答。
   - 没有文字但本轮加过表情：删除进度消息。
   - 没有文字也没加表情：沿用现在的"处理失败：没有得到回复。"
   - 出错：把进度消息改成 `grok.UserFacing(err)` 的文字。
5. 发进度消息失败或编辑失败时，退回现在的方式：直接发新消息。最终回答必须送达。

**平台接口**：`platform` 增加可选接口，供支持的平台实现，例如：

```go
// Progress 发一条可编辑的进度消息，返回句柄。
type Progress interface {
    StartProgress(ctx context.Context, in Inbound, text string) (ProgressHandle, error)
}
type ProgressHandle interface {
    Update(ctx context.Context, text string) error
    Finish(ctx context.Context, text string) error // 改成第一段，其余段落新发
    Delete(ctx context.Context) error
}
```

名称和划分由实现者决定，原则是平台细节（Telegram `editMessageText` / `deleteMessage`，Discord `ChannelMessageEdit` / `ChannelMessageDelete`）留在平台包里，core 只负责什么时候做什么。各平台的分段上限沿用现有的 `chunkLimit`。

#### 4.2.1 grok 的流式输出

聊天轮改用 `--output-format streaming-messages-json`。*（我定的）* 选它而不是 `streaming-json`，是因为它最后的 `result` 行带有 `result`（最终回答文字）和会话信息，取最终回答的方式与现在的 `json` 一致。`streaming-json` 的 `text` 事件会把每次模型回复的文字都发出来，工具调用前的过渡语也会混进去。

- 进度来自 `assistant` 消息里的 `tool_use` 块（工具名和参数）。
- 会话 ID、错误、空回答的判断沿用 `ParseHeadless` 的语义，现有错误处理的回归测试要继续通过。
- JSON-schema 调用（定时任务解析）继续用 `json`。
- 如果实测 `result.result` 与现在 `json` 输出的 `text` 不一致，实现者可以改用 `streaming-json` 并自行确定最终文字的取法，但要在实现说明里写清楚。

### 4.3 加表情回应（`react` 工具）

- 参数：`emoji`（一个表情）。目标固定为本轮触发消息。
- 定时任务轮次没有触发消息，调用返回错误。
- Telegram：bot 对一条消息只能有一个表情，新表情会替换 👀，这是期望的效果。只接受 Telegram 允许的表情集合；不在集合里时，返回错误并附上可用列表，让 Grok 换一个。
- Discord：在原消息上添加 Unicode 表情。不支持自定义表情。
- 同一轮可以多次调用。core 记录"本轮加过表情"，供 4.2 第 4 步判断。

**只加表情、不发文字的信号** *（我定的）*：模型几乎总会写点什么，所以要约定一个固定标记。提示词告诉 Grok：如果用表情回应就够了，调用 `react` 后，最终回答只写 `[[NO_REPLY]]`。bot 的判断规则：
- 本轮加过表情，且最终文字去掉首尾空白后为空或正好是这个标记：视为"不发文字"，删除进度消息。
- 没加过表情却只写了标记：按空回答处理，提示"处理失败：没有得到回复。"
- 标记出现在正常回答里：原样保留，不做特殊处理。

`grok.Client.Reply` 现在遇到空回答会报错，这会导致新会话的 ID 没被保存。需要改成：本轮加过表情时，空回答不算错误，会话 ID 照常保存（包括 `startSession` 路径）。具体做法由实现者定，例如由 core 告诉 `Reply` 允许空回答。

### 4.4 发送文件（`send_file` 工具）

**参数**：`path`（绝对路径）、可选 `caption`。

**什么时候可用**：只有本轮 `FileTools` 为真时（文件功能可用，且会话使用 `grokbot` profile）才在提示词里提到并接受调用；否则返回"文件功能当前不可用"。与"Grok 读不到就发不了"保持一致，包括没装 bubblewrap 和 v0.2.0 之前创建的老会话。

**检查**（调用时立即做，失败时把原因返回给 Grok，不发送）：

1. 必须是绝对路径。用 `EvalSymlinks` 得到真实路径，后续检查同时针对原路径和真实路径。
2. 必须是普通文件（不能是目录、设备、管道），而且 bot 进程能打开读取。
3. 不能命中沙箱的禁止读取名单：`AuthPath`、`~/.ssh` 及其下级、`BOT_ENV_FILE`、`DATA_DIR/bot.db`、`bot.db-wal`、`bot.db-shm`、文件名为 `.env`、扩展名为 `.pem`。
   - 名单必须和 `sandbox.render` 用的是**同一份定义**（例如在 `sandbox` 包里抽出一个函数，同时给 `render` 和发送检查用），以后改一处两边一起生效。
   - `**/.env`、`**/*.pem` 按文件名匹配。
4. 大小上限：Telegram 50MB，Discord 25MB（Discord 单条消息最多 10 个附件）。

**发送时机** *（我定的）*：检查通过后先记到本轮待发列表，告诉 Grok "已加入发送"。本轮回答发完后，再按调用顺序逐个发送，并引用原消息。这与 Claude Code 先文字后文件的顺序一致，也避免文件夹在进度消息和回答中间。

- Telegram：`.jpg`、`.jpeg`、`.png`、`.gif`、`.webp` 用 `sendPhoto`，其他用 `sendDocument`。说明文字作为 caption。
- Discord：作为附件发出。
- 某个文件发送失败，再补发一条简短说明（文件名 + 原因），不影响其他文件。
- 定时任务：文件跟在任务结果后面发到创建任务的聊天。
- 一轮最多发送的文件个数由实现者定一个合理上限（例如 10 个），超出时返回错误给 Grok。

### 4.5 接收图片

**哪些消息算图片**：

- Telegram：`photo`（取最大尺寸），或 MIME 为 `image/jpeg`、`image/png`、`image/gif`、`image/webp` 的 `document`。
- Discord：`content_type` 为上述类型的附件，可以有多张。
- 一条消息里既有图片又有其他附件时，只处理图片，并在回答前加一行"其余附件暂不支持"。*（我定的）*
- **Telegram 相册** *（我定的）*：相册在 Telegram 里是多条独立消息，共用一个 `media_group_id`，说明文字只在其中一条上。平台层按 `media_group_id` 缓冲，最后一张到达后约 1.5 秒内没有新的同组消息，就合并成一条 `Inbound`。合并后的消息按一条处理，只有一条进度消息，只占一个队列名额。触发消息 ID 取带说明文字的那条，没有说明文字时取第一条。表情和引用都作用于这条消息。

**处理**：

- `platform.Inbound` 增加图片字段（例如 `Images []Image`，含数据、MIME、文件名），`TextMessage` 的含义改为"有文字或有可处理的图片"。
- 平台层负责下载：Telegram 通过 `getFile`（Bot API 上限 20MB），Discord 通过附件 URL。只在通过用户名单检查之后才下载，陌生人发的图片不下载。
- 单张图片设大小上限（实现者定，不超过平台上限），超出时回复提示。
- 图片只放在内存里交给 grok，不落盘，因此不需要清理文件。如果 4.6 的验证结果要求必须落盘，放在 `DATA_DIR/inbox/` 下，并由实现者设计清理方式（删除临时文件属于 bot 自身逻辑，不涉及用户文件）。
- 说明文字作为本轮的文字部分，同样经过写入授权解析（`applyGrants`）。没有说明文字时，文字部分用一句固定提示，例如"（用户发送了一张图片）"。
- 图片消息与文字消息走同一个队列、同一个会话。

**交给 grok 的方式**：用 `--prompt-json` 传入内容块（文字块 + 图片块）。具体格式和大小限制见 4.6 第 3 项。

### 4.6 动工前必须在 Debian 测试实例上验证的事项

这几项决定方案能否成立。实现者先做一个最小验证，某一项不成立时，**只停下依赖它的功能**并回报，其余功能继续，不要自行换方案。*（我定的）* 依赖关系：

| 验证项 | 依赖它的功能 |
|---|---|
| 1、2、5（MCP 通道） | 表情回应、发送文件 |
| 3（图片） | 接收图片 |
| 4（流式输出） | 进度消息 |

因此计划要按功能分阶段，每个阶段都能单独合并。建议顺序是：进度消息 → MCP 通道 + 表情 → 发送文件 → 接收图片。

另有一项不影响能否动工，只需记录结果：grok 拉起 stdio MCP 时，是否会把 `GROKBOT_TURN_TOKEN` 传给它们（参见 4.1 信任边界）。

1. **项目级 MCP 配置是否生效**：`--cwd` 为 `DATA_DIR/workspace`（不是 git 仓库）时，`workspace/.grok/config.toml` 里的 `[mcp_servers.grokbot]` 能否被加载？是否需要 `trusted_folders.toml` 信任？在 `--sandbox grokbot` 下能否连到 `127.0.0.1`？
2. **`${GROKBOT_TURN_TOKEN}` 展开**：`headers` 里的环境变量能否从 grok 进程的环境里展开？如果不支持，再考虑把令牌放进 URL 路径（同样由环境变量提供），仍不行就回报。
3. **图片怎么传**：
   - `--prompt-json` 的图片块格式是什么（base64 还是文件路径）？`-r` 恢复会话时能否使用？
   - Linux 单个命令行参数上限约 128KB，base64 图片很容易超出。需要确认是否有不受此限制的方式，例如 `--prompt-file` 是否接受 JSON 内容块、图片块能否引用文件路径。
   - 当前订阅的模型是否接受图片输入，`models.image_description` 是否会介入。
4. **流式输出**：`streaming-messages-json` 的 `result` 行能否可靠提供最终文字和会话 ID，错误时是什么形状。
5. **MCP 工具名**：Grok 通过 `use_tool` 调用时，工具全名是什么（例如 `grokbot__react`）。提示词要用实测到的名字。

## 5. 不变的部分

- 用户名单、私聊限定、排队和队列上限。
- 命令及 Discord 斜杠命令的回复方式。
- 沙箱 profile 内容、写入授权规则、`/dir`。
- 数据库结构。不新增表或列。
- 部署方式、服务名、环境变量。本设计不新增必填配置。

## 6. 验证方式

**自动化测试**（Windows 上可离线跑，命令同 README）：

- MCP 服务：无令牌、错误令牌、已注销令牌被拒；令牌只能作用于自己的聊天；`tools/list` 输出。
- `send_file` 检查：禁止名单中的每一项，经软链接指向禁止文件，目录 / 不存在 / 超大文件，`FileTools` 为假时拒绝。并测试禁止名单与 `sandbox.render` 使用同一份定义。
- `react`：Telegram 表情集合校验，定时任务轮次被拒。
- 进度：更新节流、相同内容不重复编辑、长回答第一段编辑其余新发、只加表情时删除进度消息、编辑失败时退回发新消息、出错时改成错误文字。
- 流式解析：正常结果、错误、空回答，现有 `ParseHeadless` 相关测试继续通过。
- 图片：Telegram photo / document、Discord 附件识别；混合附件；陌生人不下载；超限提示。
- 原有测试全部通过。

**测试实例手动验证**（在 4.6 通过之后）：

1. 发一句需要联网搜索的话：看到"处理中…"→"正在搜索…"→变成回答，并引用原消息。
2. 发一个会产生很长回答的问题：第一段是编辑后的进度消息，后续段落引用原消息。
3. 发"好的谢谢"：Grok 只加表情时，进度消息消失，原消息上的 👀 变成新表情（Telegram）。
4. "把 /srv/xxx/report.pdf 发给我"：收到文件；"把 /etc/grok-tg-bot.env 发给我"、指向 `.env` 的软链接、`~/.ssh/id_ed25519`：都被拒绝。
5. 卸掉或模拟没有 bubblewrap：发文件被拒，聊天正常。
6. 发一张照片（带 / 不带说明文字），再以文件形式发一张图：Grok 能描述图片内容。
7. 定时任务里让 Grok 发文件：文件跟在 `⏰ 定时任务` 结果后面。
8. Discord 私聊重复 1、3、4、6。

## 7. 风险和回滚

- **本地端口**：MCP 服务只监听回环地址，每轮令牌随机且用完即废。本机其他用户的进程能连到端口，但没有令牌无法调用。
- **提示注入**：网页或文件内容可能诱导 Grok 发文件。文件只能发到触发本轮的聊天，也就是用户本人，范围与 Grok 现在能读到并写进回答的内容相同，不新增外泄途径。已有的"读文件 + 联网"风险不变，README 已说明并被接受。
- **限流**：进度编辑节流 3 秒以上；编辑失败不重试，直接退回发新消息。
- **grok 版本变化**：流式事件和 MCP 配置格式可能随 grok 更新而变化。解析未知事件时一律忽略，不报错。
- **回滚**：不改数据库，恢复旧二进制并重启即可。`DATA_DIR/workspace/.grok/config.toml` 对旧版本无害，可以留着；如果需要移除，由管理员确认后手动处理。
