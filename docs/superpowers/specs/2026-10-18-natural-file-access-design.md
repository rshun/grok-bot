# 自然语言文件访问：设计说明

日期：2026-10-18
分支：`dev-natural-file-access`（基于 `origin/master` a0e0457，即 v0.2.0）
前置设计：`docs/superpowers/specs/2026-10-18-web-files-tasks-design.md`

## 1. 背景和目的

v0.2.0 的文件访问要求先用 `/dir add ro|rw` 把目录加进名单，沙箱以 `strict` 为基础，只能读名单里的目录。实际使用时，用户直接对 Grok 说"看看 /srv 里有什么"，结果读不到。用户不想用 `/dir` 这类命令，希望：

- **读**：交给系统权限管。直接说"请访问 /srv/summer"，只要运行 bot 的系统用户有权限读，Grok 就能读。
- **写**：必须由用户在消息里明确说出"允许写入 /srv/out"这类话。授权一直保留，直到用户明确取消。
- **执行**：任何文件和命令都不允许执行。

## 2. 目标、非目标、反目标

**目标**

- 读权限由服务用户自身的 Unix 权限决定，bot 不再维护"可读名单"。
- 用自然语言授予、取消写权限，由 bot 解析用户本人发的消息，授权永久保存。
- shell 和命令执行工具保持禁用。

**非目标**

- 不做按聊天区分的写权限（名单仍然所有聊天共用）。
- 不做临时授权。
- 不自动替换老会话。
- 不改数据库结构。

**反目标（即使功能能用，出现以下情况也算失败）**

- Grok 自己，或者网页、文件里的内容，能让 bot 新增可写目录。
- 能读到 grok 登录凭证、`~/.ssh`、bot 的环境文件、`bot.db`、`.env`、`.pem`。
- Grok 能执行任何文件或命令。
- 升级后老会话的上下文被自动清空。
- Grok 能改写沙箱配置，从而扩大可写范围。

## 3. 用户已经决定的

| 事项 | 决定 |
|---|---|
| 读 | 由系统权限控制。提到路径就能读，不需要授权 |
| 写 | 消息里必须明确说"允许写入 <路径>"，只说"写到 /srv/out"不算 |
| 写权限保留多久 | 一直保留，直到用户明确取消 |
| 执行 | 一律禁止 |
| 老会话 | 保留上下文；涉及文件时在回复里提醒发 `/reset` |

## 4. 设计

### 4.1 沙箱 profile

`grokbot` profile 的内容改为：

```toml
# managed by grok-bot; do not edit
[profiles.grokbot]
extends = "read-only"
restrict_network = false
read_write = [<可写名单>]
deny = [<与 v0.2.0 相同>]
```

- `read-only` 基础 profile 的规则是：哪里都能读，只能写 `~/.grok/`、`/tmp`、`/var/tmp`。在此基础上，再用 `read_write` 加上可写名单。
- 不再生成 `read_only` 字段。
- `deny` 列表不变：`AuthPath`、`~/.ssh`、`BOT_ENV_FILE`、`DATA_DIR/bot.db`、`DATA_DIR/bot.db-wal`、`DATA_DIR/bot.db-shm`、`**/.env`、`**/*.pem`。
- profile 名称还是 `grokbot`。v0.2.0 创建的 `grokbot` 会话恢复时，如果 grok 会重新读取 profile 内容，就自动换成新规则；如果不会，就继续沿用 `strict`。沿用 `strict` 只是能读的范围更小，不会扩大权限。
- 预期这样能修好 Theseus-mcp 这类本地启动的 MCP：`strict` 限制子进程只能读工作目录，换成 `read-only` 之后就没有这个限制了。

### 4.2 写权限的自然语言解析

解析只在**普通聊天消息**进入 Grok 之前，由 bot 在 core 里完成，用的是确定的规则，不调用 Grok。以下几种情况**不做解析**：

- 命令；
- 定时任务执行时的 prompt；
- `/task` 后面的文字。

**授权**：消息里出现授权短语，紧跟在后面、同一分句里的绝对路径，就是要授权的路径。

- 授权短语：`允许写入`、`授权写入`、`允许写`、`可以写入`。
- 分句的边界：`，`、`。`、`；`、`！`、`？`、`,`、`;`、换行。
- 同一分句里可以有多个路径，用空格、`、`、`和`、`及` 隔开。
- 路径的定义：以 `/` 开头，一直到空白或上面列出的分隔符为止。
- 路径末尾如果是 `的`、`目录`、`文件夹`、`里`、`下`，会先去掉再检查，例如"允许写入 /srv/out目录"会按 `/srv/out` 处理。路径中间的中文保留，因为目录名本身可能是中文。
- 例子：
  - "允许写入 /srv/out，然后读 /srv/summer"：只授权 `/srv/out`；
  - "允许写入 /srv/a 和 /srv/b"：两个都授权。

**取消**：有两种句式。

- 句式一：取消短语后面紧跟路径，取消短语为 `取消写入`、`禁止写入`、`撤销写入`、`收回写入`。
- 句式二：同一分句里，`取消`、`撤销` 或 `收回` 后面依次出现路径和 `写入权限`（或 `写权限`），例如"取消 /srv/out 的写入权限"。
- 取消之后，要从名单里删掉这个目录。删除时，先按原样的路径匹配；匹配不到，再把路径清理（`Clean`）、解析软链接（`EvalSymlinks`）之后再匹配一次。

**处理**：

- 授权的路径要经过 v0.2.0 的 `Policy.CheckDir` 检查：必须存在、是目录、不在黑名单里、按真实路径判断。检查通过，就以 `rw` 写入 `dirs` 表。
- 授权或取消的结果，作为一行确认加在 Grok 回复的前面：
  - 成功：`已允许写入 /srv/out。`、`已取消 /srv/out 的写入权限。`
  - 失败：`没有允许写入 /etc：不能开放 /etc 及其上下级目录。`
- 整条消息照常发给 Grok，同一轮里继续完成用户的其他要求。比如"允许写入 /srv/out，把总结保存到 /srv/out/a.md"。*（我定的）*
- 授权成功后，要在本轮调用 grok **之前**重写 profile，这样本轮就能写进去。
- 第一次授权时，如果 profile 文件不受 bot 管理（就是 v0.2.0 的 `ErrUnmanaged`），仍然把授权写入 `dirs` 表，同时在确认行后面附上不可用的原因。

### 4.3 文件工具和系统提示词

- 带 `grokbot` 的会话开放这五个文件工具：`read_file`、`list_dir`、`grep`、`search_replace`、`write`。写到名单以外的地方，由内核拒绝。
- shell 类工具（`run_terminal_cmd`、`run_terminal_command`）、子代理等，继续禁用。
- 系统提示词里的文件部分改成：

  > You may read any file the system lets you read. You may write only in: <名单，没有时写 (none)>. Writing is granted only when the user says so; never claim you can grant it. Never run files or commands.

  原来提示词里的 `Do not use the shell` 保留。

### 4.4 老会话提醒

只要同时满足以下三个条件：

- 这个聊天的会话是 v0.2.0 之前创建的（`chats.sandbox` 不是 `grokbot`）；
- 文件功能可用（`fileAccess` 返回 `ready`）；
- 用户的消息里含有绝对路径，或者含有授权、取消短语；

就在 Grok 回复的**最后**加一行：

> 提示：这个聊天的会话创建于开启文件功能之前，发送 /reset 后才能读写本机文件（会清空这个聊天的上下文）。

上下文不做任何改动。

### 4.5 `/dir` 命令

`/dir` 保留，作为查看和兜底的手段：

- `/dir`：列出可写目录，并说明"读取由系统权限控制"。原有的老会话提示、不可用原因照常显示。
- `/dir add rw <路径>`、`/dir del <路径>`：行为不变。
- `/dir add ro <路径>`：回复"读取由系统权限控制，不需要开放。"，不写库。
- `dirs` 表里 v0.2.0 留下的 `ro` 记录：不读取、不显示、也不删除。*（我定的：不动数据，回滚到 v0.2.0 时还能用。）*

### 4.6 定时任务

定时任务执行时，和普通新会话一样带 `grokbot`，读写规则相同。执行时不做写权限解析，所以授权只能来自用户实时发的消息。

## 5. 风险，以及需要用户知道的

- **读取范围明显扩大。** 凡是服务用户能读的文件，Grok 都能读，包括 `/srv` 下其他程序的配置。deny 列表只能挡住常见的几种敏感文件。建议用专门的系统用户运行服务，不要让它能读到不该给 Grok 看的东西。
- **可能被诱导泄露数据。** 联网读网页（`web_fetch`）和能读本机文件同时开着时，网页内容可能诱导 Grok 去读本机文件，再把内容拼进它访问的网址里发出去。目前的保护只有 deny 列表和服务用户自身的权限。**用户已决定保留 `web_fetch`，接受这个风险**（2026-10-18）。
- **沙箱配置可能被改写。** `read-only` 基础 profile 允许写 `~/.grok/`。如果 `~/.grok/sandbox.toml` 不在 grok 的写保护范围内，Grok 就能改写它、扩大自己的可写范围。这一点必须在服务器上实测。如果确实能写，就把它加进 `deny` 再测；如果加进 `deny` 之后 grok 无法启动，就停下来请用户决定。

## 6. 必须在服务器上实测的

以下几项全部通过之前，不要授权任何写入目录：

1. `~/.grok/sandbox.toml` 在新 profile 下确实写不进去（让 Grok 尝试写一次）。
2. 禁止读取 `auth.json` 之后，grok 能正常回复。
3. 新会话里 Theseus-mcp 等 MCP 能正常连接。
4. 读取：服务用户能读的目录可以读；`~/.ssh`、环境文件读不到。
5. 写入：名单里的目录可以写；名单以外（包括 `/srv` 下没授权的目录）写不进去。
6. v0.2.0 创建的 `grokbot` 会话恢复后，是否用上了新规则（只用于确认，不影响上线）。

## 7. 验证

- 单元测试，至少覆盖：
  - 授权、取消的解析：分句边界、多个路径、路径末尾的 `的`，以及"允许写入 /a，然后读 /b"只授权 `/a`；
  - 黑名单路径的授权失败时，回复里有对应的确认行；
  - 新 profile 的内容（`extends = "read-only"`，没有 `read_only` 字段）；
  - 老会话收到含路径的消息时，回复末尾有提醒，上下文不变；
  - `/dir add ro` 的新回复；
  - 定时任务执行时不做授权解析。
- 测试实例上手动检查：
  1. "看看 /srv 里有什么"能列出内容；
  2. "把 hello 写到 /srv/out/a.txt"被拒绝；
  3. "允许写入 /srv/out"之后再写，成功；
  4. "取消 /srv/out 的写入权限"之后再写，又被拒绝。

## 8. 回滚

换回 v0.2.0 的二进制并重启。v0.2.0 下一次调用 grok 时，会把 profile 重写回 `strict` 版本。`dirs` 表里的 `rw` 记录在 v0.2.0 里照样有效。数据库不需要改动。
